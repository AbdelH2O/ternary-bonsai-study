# Matching Prism ML's ternary Bonsai models: an independent study

An independent research project. The goal is to match the results of Prism ML's ternary (1.58-bit) Bonsai language models, starting from the same public Qwen base models, in the same packed format, under the same evaluation. It is **not affiliated with or endorsed by Prism ML**.

**Where to start:**
- [replication/RESEARCH_LOG.md](replication/RESEARCH_LOG.md): the chronological record of every step, decision, failure and correction, with links to the evidence.
- [replication/REPLICATION_PLAN.md](replication/REPLICATION_PLAN.md): the questions and the standard of evidence.
- [replication/QAT17B_DESIGN.md](replication/QAT17B_DESIGN.md): the current 1.7B training design (draft).
- [replication/PRISM_FORENSICS_17B.md](replication/PRISM_FORENSICS_17B.md): what Prism's released 1.7B files reveal.
- Experiment reports, each leading with its predeclared decision: [PHASE1_17B.md](replication/PHASE1_17B.md), [QAT08.md](replication/QAT08.md), [QAT08_CHAT.md](replication/QAT08_CHAT.md), [QAT08_MCU.md](replication/QAT08_MCU.md), [CODE_DRIFT.md](replication/CODE_DRIFT.md).

**How the work is done:** designs and protocols are frozen and hashed before any GPU run, and reports lead with the frozen decision. Model weights, checkpoints and other large artifacts aren't in the repository; the reports record their SHA-256 hashes.

**Third-party content.** The repository includes evaluation and training-prompt material from public sources, each under its original licence. Each report names the pinned revisions. Sources:
- Project Gutenberg books;
- MMLU and MMLU-Redux;
- GSM8K;
- ARC;
- LongBench subsets;
- NVIDIA Daring-Anteater prompts;
- FineWeb-Edu passages.

It also includes outputs generated by Qwen3/Qwen3.5 models and by Prism ML's Bonsai models (Apache 2.0), and quotes from Prism ML's public whitepapers and model cards, for analysis.

# Bonsai 2 27B: compact versus full precision

This is a lightweight structural analysis of the **local Bonsai 2 27B `PQ2_0` checkpoint** against its full precision Qwen3.8-27B reference. It reads the GGUF header and a small, evenly spaced sample of packed groups. It does not load the model into RAM or VRAM. Task scores come from [Prism ML's September 2026 whitepaper](https://github.com/PrismML-Eng/Bonsai-demo/blob/main/bonsai-2-27b-whitepaper.pdf), Tables 8, 10 and 11; we have not reproduced those scores here.

## What the local checkpoint shows

The downloaded model has 64 language blocks in the repeating pattern `linear, linear, linear, full` (16 cycles). This matches [Qwen3.8-27B's architecture config](https://huggingface.co/Qwen/Qwen3.8-27B/blob/main/config.json). The header lists 851 tensors:

| Storage | Tensors | Parameters | Packed bytes |
| --- | ---: | ---: | ---: |
| `PQ2_0` ternary g128 | 402 | 26,869,760,000 | 7,137,280,000 |
| BF16 | 96 | 23,592,960 | 47,185,920 |
| F32 | 353 | 2,645,504 | 10,582,016 |

Thus **26,238,464 parameters, or 0.0976% of this language checkpoint, remain above ternary precision**. The tensor counts and parameter count agree with whitepaper Table 2. The GGUF's actual higher precision bytes total 57.8 MB because the small normalization and state tensors are F32 in this pack; the paper's 52 MB figure is the BF16 equivalent for all 26.2 million parameters.

The header names 401 rotated matrix tensors. The remaining ternary tensor is `token_embd.weight`, whose metadata declares an inverse transform after lookup. This matters for any future weight comparison: the stored ternary matrices are in a Hadamard rotated basis, so subtracting their packed values from ordinary Qwen weights would be meaningless without decoding and applying the matching basis transform.

## Region map and likely sensitivity

| Region | Blocks | What the checkpoint keeps above ternary precision | Why it may matter |
| --- | --- | --- | --- |
| Recurrent state path | 48 linear attention blocks | `ssm_alpha`, `ssm_beta` in BF16; convolution, state rate/bias and state norm in F32 | Small errors in state updates can persist across many tokens. This is a plausible reason for preserving this path. |
| Normalization | All 64 blocks plus final norm | F32 attention and post-attention norms; F32 query/key norms in 16 full attention blocks | A norm changes the scale of every downstream feature, so errors can propagate broadly. |
| Attention and MLP projections | All 64 blocks | Ternary | Large matrices dominate size; the rotated basis and trained ternary weights make them compressible in this design. |
| Embedding and output head | Model endpoints | Ternary | Each has 1.27 billion parameters; keeping these high precision would consume much of the memory budget. |

Per linear attention block, **542,944 parameters** remain BF16/F32. Per full attention block, **10,752** remain F32. Across the whole model, 25,569,792 of the preserved parameters (97.45%) belong to the recurrent state path and 668,672 (2.55%) to normalization. This is an exact storage map, not an ablation result. The causal explanations in the right column are hypotheses; the whitepaper does not publish per-region ablations.

## What the packed weights look like

The sampler read 32 evenly spaced 128-weight groups from each of the 402 ternary tensors: **12,864 groups**, or 1,646,592 decoded weight codes. It uses the [Prism fork's `PQ2_0` decoder](https://github.com/PrismML-Eng/llama.cpp/blob/prism/ggml/src/ggml-quants.c) to identify zero codes. Of these, **12,507 groups (97.2%) have exactly 42 zeros**. No invalid `PQ2_0` codes appeared. The sampled zero fraction is about 32.7% in every broad region. This strongly suggests a constrained or balanced assignment of ternary codes, but the training recipe is not public enough to establish why. It also means that ranking regions by their zero fraction is unlikely to reveal importance. This is a tiny, tensor-balanced sample, not a full-model sparsity estimate.

Group scales differ by tensor and operation. A larger scale alone does not mean a layer is more important: activation distributions, normalization, and the rotated basis all affect the output error from the same weight perturbation.

## What the published behavior says

The table below is Bonsai minus Qwen3.8 FP16 in percentage points, calculated from the paper's per-benchmark rows. A positive number favors Bonsai.

| Category | `xhigh` | `medium` |
| --- | ---: | ---: |
| Knowledge and reasoning | -2.71 | -4.14 |
| Math | -0.49 | -5.40 |
| Coding | -0.59 | -2.78 |
| Instruction following | +1.41 | -0.02 |
| Agentic and tool calling | -2.16 | -5.50 |
| Vision | -3.05 | -2.22 |

The 20-benchmark overall mean is 83.9 versus 85.4 at `xhigh`, and 79.3 versus 82.6 at `medium`. The larger gaps at medium effort are most visible on AIME25 (-11.67), GPQA Diamond (-8.78), and τ²-Bench (-8.64). This suggests additional reasoning time may help compensate for compression on some tasks, but it is not proof of the mechanism. Long agent runs expose a larger gap: Terminal-Bench 2.1 is 52.8 versus 69.7, and SWE-bench Verified is 60.8 versus 80.6. Vision scores also involve a separately packed vision tower, so they cannot isolate language-weight effects.

The structural and behavioral observations do **not** establish that a particular numbered block caused a task failure. To make that claim, we would need controlled changes to one region at a time, the same prompts and decoding settings, and repeated scores. Comparing the two models' final answers alone can locate vulnerable tasks, but not the internal cause.

## Controlled perturbation pilot on a 12 GB GPU

The [experiment plan](EXPERIMENT_PLAN.md) compares the original Bonsai model with copy-on-write GGUF variants that perturb its recurrent gates and an equal-size MLP control. It uses paired short and long retrieval prompts, then a frozen subset of natural long-context questions. Each arm ran alone at 16K context; no full precision Qwen checkpoint was needed. The [calibration report](CALIBRATION_REPORT.md) records the GPU and short-context checks, which did not yield two measurably damaging, matched arms. An explicitly exploratory [frozen pilot](PRIMARY_FREEZE.json) then completed all 440 requests. Every arm answered all 24 paired retrieval questions at both lengths, but a later audit found that the correct code has a unique prefix in every primary prompt, letting a question-blind text search solve 48/48. Answer-logprob contrasts were tiny and changed sign across strengths. Natural QA changes affected two Qasper items only in the 2% state arm and one 2Wiki item in both 3% arms. The [experiment report](EXPERIMENT_REPORT.md) gives the paired intervals, item-level results, and limits. These results do not establish a causal map or rule out recurrent-error accumulation on harder questions.

## Reproduce the inexpensive local analysis

From the repository root:

```bash
MODEL=models/bonsai2-gguf/27B/Ternary-Bonsai-2-27B-PQ2_0.gguf
python3 analysis/bonsai2/inspect_gguf.py "$MODEL"
python3 analysis/bonsai2/sample_ternary.py "$MODEL"
python3 analysis/bonsai2/analyze_scores.py
```

`inspect_gguf.py` reads about 11.1 MB of header metadata. `sample_ternary.py` seeks to under 0.5 MB of packed weight blocks; it does not read or unpack the whole 7.2 GB file. The generated [region summary](results/regions.csv), [per-block map](results/blocks.csv), [tensor map](results/tensors.csv), [sample results](results/sampled_regions.csv), and [benchmark deltas](results/benchmark_deltas.csv) are included for inspection. This analysis can run on CPU alone.
